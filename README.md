# CS 250: Software Development Lifecycle

This repository contains my Sprint Review and Retrospective from the CS 250 final project at Southern New Hampshire University. The project simulated a Scrum pilot for SNHU Travel, a travel booking application, and I worked through each Scrum role: Product Owner, Tester, Developer, and Scrum Master.

## Reflection

### How do I interpret user needs and implement them into a program? How does creating user stories help?

I start by finding out why users want a feature, not just what they ask for. In the SNHU Travel focus group, customers explained that a generic destination list was useless to someone who never travels to the tropics, and that reasoning became the personalization and filtering stories. User stories capture that intent in a form every role can work from. The value statement keeps the purpose visible, and measurable acceptance criteria, such as a filter updating within two seconds, turn directly into pass/fail tests. Because the tests existed before implementation, I knew what "done" meant before writing any code.

### How do I approach developing programs? What Agile processes do I hope to incorporate into my future development work?

I treat requirements as the start of a conversation, not a finished specification. When something is undefined, I raise it with the people who own the decision instead of guessing. During this project, fixing a layout defect exposed a readability problem that no requirement covered, so I asked the Product Owner and Tester rather than deciding on my own. In future work, I want to keep an ordered backlog with relative sizing, write test cases alongside development, maintain a clear Definition of Done, and hold regular retrospectives. This project changed direction twice, and working in short iterations let the team absorb both changes by adjusting scope instead of extending the deadline.

### What does it mean to be a good team member in software development?

Being a good team member means communicating in ways that are specific, tied to the work, and easy to answer. When I needed decisions, I asked each person only the questions they could answer, explained why the answers mattered, and set a deadline tied to a Scrum event. I copied the Product Owner and Tester on the same thread so each could see the other's decisions. It also means keeping shared tools honest. A task board that is not kept current gives a false picture of progress, much like an aircraft maintenance work order that does not match the actual state of the aircraft, something I learned during 17 years in aircraft maintenance. Good teammates also give credit where it is due and make it easy for others to do their part.
